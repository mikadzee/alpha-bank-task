# Backend ТЗ — текущий frontend MVP

## Задача

Подготовить API для клиентского сценария личного кабинета Альфа-Банка:

1. Клиент регистрируется или входит по email и паролю.
2. На главной видит свои заявки и их текущие статусы.
3. Создаёт заявку и заполняет данные компании и финансов.
4. Загружает документы, получает варианты кредита и отправляет заявку.
5. После обновления страницы продолжает работу с сохранённым черновиком.

Дизайн главной страницы, формы заявки и экранов входа/регистрации сохраняется. Этот документ описывает текущий объём backend; отложенные функции перечислены в конце.

## Авторизация

Публичная регистрация создаёт пользователя с ролью client. Вход — только по email и паролю. Телефон, SMS, QR-код, восстановление пароля и публичная регистрация сотрудников не нужны.

### Методы

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| POST | /api/v1/auth/register | Регистрация клиента |
| POST | /api/v1/auth/login | Вход клиента |
| GET | /api/v1/auth/me | Текущий пользователь |
| POST | /api/v1/auth/refresh | Обновление access-токена |
| POST | /api/v1/auth/logout | Завершение сессии |

Регистрация принимает:

    {
      "email": "client@example.test",
      "password": "StrongPass123",
      "passwordConfirmation": "StrongPass123"
    }

Пароль — минимум 8 символов; подтверждение совпадает с паролем. Email уникален.

Успешный вход и регистрация возвращают:

    {
      "accessToken": "<token>",
      "user": {
        "id": "<uuid>",
        "email": "client@example.test",
        "role": "client"
      }
    }

Access-токен фронтенд хранит в памяти вкладки и отправляет как Authorization: Bearer <accessToken>. Для продления сессии backend устанавливает refresh-токен в HttpOnly cookie. /auth/refresh выдаёт новый access-токен и ротирует cookie; /auth/logout отзывает refresh-токен и очищает cookie. Эти два маршрута добавлены в frontend-контракт, потому что в исходном ТЗ их не было.

GET /auth/me возвращает id, email, role. В шапке имя компании и ИНН берутся из сохранённой заявки, email и роль — из профиля пользователя. Публичная регистрация создаёт только клиента. Локальный demo-сотрудник создаётся при запуске из `DEMO_EMPLOYEE_EMAIL` и `DEMO_EMPLOYEE_PASSWORD`.

## Заявка клиента

Каждая заявка принадлежит авторизованному клиенту. Клиент может видеть только свои заявки. Незавершённая заявка сохраняется со статусом draft; повторное открытие кабинета должно возвращать сохранённые данные.

### Методы

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | /api/v1/companies/lookup?inn=... | Поиск в локальном синтетическом справочнике |
| POST | /api/v1/applications | Создать черновик |
| GET | /api/v1/applications | Получить заявки клиента для главной |
| GET | /api/v1/applications/{id} | Получить заявку и восстановить форму |
| PATCH | /api/v1/applications/{id} | Сохранить данные черновика |
| GET | /api/v1/applications/{id}/recommendations | Подобрать демонстрационные продукты |
| POST | /api/v1/applications/{id}/documents | Загрузить документ |
| POST | /api/v1/applications/{id}/submit | Выбрать продукт и отправить заявку |

При создании черновика вернуть { "id": "<uuid>", "status": "draft" }.

### Данные компании

companyData:

- inn — 10 цифр для юридического лица или 12 для ИП, обязательно;
- companyName — обязательно;
- okved — обязательно, например 28.99;
- ogrn и address — необязательные.

Результат поиска компании:

    {
      "found": true,
      "company": {
        "inn": "7701234567",
        "ogrn": "1237700123456",
        "companyName": "ООО ТехноПлюс",
        "address": "г. Москва, ул. Примерная, д. 10",
        "okved": "28.99"
      }
    }

Для неизвестного ИНН вернуть found: false; ручное заполнение должно оставаться доступным. Использовать только синтетические компании. Подключение ФНС не нужно.

### Финансовые данные

financialData:

    {
      "annualRevenue": 12000000,
      "monthlyExpenses": 700000,
      "requestedAmount": 2000000,
      "requestedTermMonths": 24,
      "purpose": "working_capital",
      "purposeDetails": "Закупка товара"
    }

Все суммы — целые рубли без пробелов и знака валюты. Разрешённые purpose: working_capital, equipment, business_expansion, other. purposeDetails необязательно. Доходы и расходы неотрицательные; сумма и срок должны быть больше нуля.

Пример сохранения:

    {
      "companyData": {
        "inn": "7701234567",
        "ogrn": "1237700123456",
        "companyName": "ООО ТехноПлюс",
        "address": "г. Москва, ул. Примерная, д. 10",
        "okved": "28.99"
      },
      "financialData": {
        "annualRevenue": 12000000,
        "monthlyExpenses": 700000,
        "requestedAmount": 2000000,
        "requestedTermMonths": 24,
        "purpose": "working_capital",
        "purposeDetails": "Закупка товара"
      }
    }

PATCH разрешён для draft и возвращённой банком заявки `needs_info`; проверять владельца заявки.

## Документы

Текущий набор:

| documentType | Документ | Обязательность |
| --- | --- | --- |
| egrul_extract | Выписка из ЕГРЮЛ | Обязательно |
| accounting_report | Бухгалтерская отчётность | Обязательно |
| tax_certificate | Справка о налоговой задолженности | Обязательно |
| bank_statement | Выписка по расчётному счёту | Необязательно |
| other | Дополнительный документ | Необязательно |

Состав и обязательность документов зафиксированы по текущему макету. Принимать PDF, JPG и PNG до 10 МБ на файл. Загрузка — multipart/form-data, поля documentType и file. Для одного черновика разрешить несколько документов типа other. Ответ:

    {
      "documentId": "<uuid>",
      "type": "tax_certificate",
      "originalName": "certificate.pdf",
      "sizeBytes": 123456,
      "uploadedAt": "<ISO-8601>"
    }

Индикаторы «загружается», «ошибка» и повторная загрузка — frontend-состояния. Перед отправкой проверить наличие всех трёх обязательных типов документов. Не публиковать файлы по открытым предсказуемым URL.

## Подбор и отправка

Backend подбирает продукты из локального каталога и возвращает карточки для дизайна:

    {
      "recommendations": [{
        "productId": "turnover",
        "name": "Кредит на оборотные средства",
        "amount": 2000000,
        "termMonths": 24,
        "annualRate": 16,
        "monthlyPayment": 97926,
        "totalPayment": 2350229,
        "recommended": true,
        "reasons": ["Подходит цели"],
        "warnings": ["Условия демонстрационные"]
      }]
    }

Ставки и продукты синтетические, не являются предложением Альфа-Банка. Подбор — простые объяснимые правила; внешняя LLM и реальные банковские системы не подключаются. Авторизованный `GET /api/v1/products` возвращает демонстрационный каталог для страницы «Кредиты». `GET /api/v1/feed` формирует персональные события и отраслевые подсказки только по данным кабинета; это не внешние новости.

Отправка:

    { "productId": "turnover" }

Backend повторно проверяет заявку, документ, продукт и условия, затем переводит draft или needs_info в pending. Ответ: { "id": "<uuid>", "status": "pending", "submittedAt": "<ISO-8601>" }. Повторную отправку не дублировать.

## Кабинет сотрудника банка

Сотрудник входит через общий `/auth/login`; отдельной публичной регистрации сотрудника нет. Backend выдаёт роль employee и проверяет её на каждом банковском маршруте. При локальном запуске compose создаёт синтетическую учётную запись из `DEMO_EMPLOYEE_EMAIL` и `DEMO_EMPLOYEE_PASSWORD`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | /api/v1/staff/applications?status=pending&search=... | Очередь и фильтр заявок клиентов |
| GET | /api/v1/staff/applications/{id} | Данные заявки, документов и демонстрационная оценка платежной нагрузки |
| GET | /api/v1/staff/applications/{id}/documents/{documentId} | Безопасно скачать документ по авторизованному маршруту |
| POST | /api/v1/staff/applications/{id}/decision | Сохранить решение сотрудника |

Доступные решения: `approved`, `needs_info`, `rejected`, `counteroffer`. Для уточнения, отказа и встречного предложения сотрудник обязан оставить комментарий. Встречное предложение содержит сумму и срок в границах выбранного продукта; backend сам пересчитывает платёж. Клиент может принять или отклонить его через `POST /api/v1/applications/{id}/offer-decision`. После запроса уточнений клиент может исправить данные/документы и отправить заявку снова. В карточке сотрудника показаны исходные документы и арифметические факторы оценки; это не банковский скоринг.

## Ошибки

Единый формат:

    {
      "error": {
        "code": "VALIDATION_ERROR",
        "message": "Проверьте обязательные поля",
        "fields": {
          "requestedAmount": "Сумма должна быть больше нуля"
        }
      }
    }

Использовать HTTP 400/422 для валидации, 401 для истёкшей/невалидной сессии, 403/404 для недоступной заявки, 409 для недопустимого статуса, 413 для слишком большого файла и 415 для неподдерживаемого типа файла.

## История и навигация

`GET /api/v1/applications` возвращает также `events`, упорядоченные по времени. События отражают создание черновика, отправку, исправление после запроса, решение банка и ответ клиента на встречное предложение. Сотрудник получает ту же историю в `GET /api/v1/staff/applications/{id}`. Приложение не предоставляет API удаления заявок: черновики сохраняются. Удалить можно сохранённый профиль компании; снимок реквизитов уже созданных заявок остаётся неизменным.

Страницы `/applications`, `/loans`, `/company`, `/documents` и `/staff` доступны через навигацию. Каталог, документы и лента используют backend API.

## Отложено

Пока не реализовывать уведомления, настройки профиля, реальные тарифы, ФНС, SMS, QR и интеграцию с системами банка.

Роль employee ограничена просмотром поданных заявок, загрузкой приложенных документов и фиксацией одного из четырёх решений. Не удалять клиентский дизайн, шапку, навигацию, главную страницу, экраны заявки, входа и регистрации.
